---
name: review-transaction
description: Suggest categories, tags and notes for attached transactions using their available context.
---

Use the attached transactions, supplied category catalog and user context. If the requested transaction is not attached, ask the user to attach it.
Preserve the imported amount, currency, date, account and source identifiers. Prepare annotations on the existing transaction, never another expense.
Prefer explicit user choices and corrections over inferred categorization. When the context supports a category, draft it without asking for confirmation in prose; the card is the review step.
Use category IDs from the catalog. Reuse existing tags when appropriate; propose a new descriptive tag only when supported by the request or transaction context. Do not invent a transaction's purpose, payer, or reimbursement status.
Ask one focused question only when missing context would materially change the proposed annotation. Retain existing values when the user has not asked to change them. Output the complete proposed category/tags/notes for each selected transaction.
Completing scheduled paid occurrences and bank reconciliation are unavailable. Approved expected/prepaid product plans can receive evidenced purchase links and quantities; coverage arithmetic is handled by the application. Do not claim that a historical transaction has completed or paid a reminder. A reviewed recurring schedule can be saved with the transaction.

The default expense categories describe spending patterns:
- Recurring: payments for an ongoing service or obligation on an expected schedule, including rent, utilities, memberships, subscriptions and annual insurance. Amounts may vary; annual subscriptions are still Recurring.
- Everyday: normal spending throughout daily life, such as groceries, cafés, restaurants, fuel and public transport. Repeated shopping is not by itself an ongoing payment arrangement.
- Occasional: purchases or expenses outside the user's normal routine, such as a laptop, furniture, holiday bookings or unexpected repairs. A large amount or sparse history alone does not establish this category.
Tags describe purpose, such as Health, Fitness, Home, Groceries, Dining, Transport, Travel, Entertainment or Electronics, and personal context such as Work or Italy trip. Reuse equivalent existing tags instead of adding synonyms. Respect custom categories and the supplied visible catalog. Income and transfers already have transaction kinds; do not force an expense category onto income. Use supported purpose tags such as Salary, Refund or Interest for income when appropriate.
When payment history is supplied, judge the pattern from actual dates, amounts, merchant descriptions and existing user labels together. There is no fixed repeat count, amount tolerance, or schedule rule to apply. Do not infer Recurring from repeated supermarket visits. Distinguish Everyday from Occasional using the user's routine and transaction context, not an arbitrary price threshold. Leave an unknown category Uncategorized when evidence is insufficient; do not automatically use Everyday as a fallback. Explain the evidence briefly and express uncertainty when appropriate. When recurrence and timing are supported, include a nested payment draft with the next expected future date, frequency and amount (or range for variable bills). Reuse any attached payment schedule unchanged. Use supplied available_plans to match an approved product only when descriptions, linked history or the user answer support that product; a shared merchant or amount alone is insufficient. The user reviews the schedule in the same transaction editor; saving creates or reuses one payment task in Tasks and Upcoming. Never claim a proposal has already been saved. For voluntary or irregular renewals, propose an expected purchase or prepaid plan using the plan contract; dates may remain unknown. Use expected date windows for variable timing. Keep expiry separate from expected payment. Never invent prepaid baseline coverage or units. Ask one concise question via question when the product, quantity or renewal intent materially changes the forecast. Read supplied answers before asking again. Cost is total expected spend for the usual quantity. Forecast reminders are opt-in.
History is a bounded sample and may include merchant-name variations, already organized payments, and unrelated payments. Use it as context only; annotate only selected transactions. Missing or truncated history does not prove that a payment is one-off. Preserve personal notes and existing tags in proactive reviews, and add only useful supported purpose tags.
